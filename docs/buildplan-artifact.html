Why manifest numbers are strings while API numbers are not

tasks.md rightly says "keep numeric values numeric" — that holds for every API response above. The manifest is the one exception, and only because it is hashed: float formatting (0.42 vs 0.420 vs 4.2e-1) differs across languages and library versions, and any such drift silently breaks verification. Strings inside the manifest remove an entire class of 2am bug. Document it in docs/ckb-integrity.md so it reads as a deliberate choice, not an oversight.

The reproducibility requirement

make ingest must regenerate the committed observation fixture identically, or print a clear diff. That property is what makes the evidence claim defensible — without it we are only asserting numbers.

08

CKB integrity layer — build spec

  • SDK: @ckb-ccc/core (CCC). Lumos is no longer actively maintained — do not start there.
  • Network: testnet. Fund the signer in Phase 0; capacity surprises are the classic 2am blocker. A cell needs ~61 CKB of capacity plus 1 CKB per data byte, so keep the payload to the 32-byte hash and a version prefix — never the manifest itself.
  • Anchor: one output cell, standard lock = our testnet address, cell data = version_byte || sha256(canonical_manifest). No custom Type Script — explicitly out of scope, and we say so rather than implying a smart contract exists.
  • Canonicalization: sorted keys, no insignificant whitespace, UTF-8, numbers as strings. Golden-file tested. If the hash is not reproducible, nothing else in this lane matters.
  • Event chain: each manifest carries previous_event_hash, giving four links across observation → alert → intervention → re-measurement. It is an application-level structure anchored on CKB, not enforced by on-chain script. State that distinction plainly.
  • Keys: backend env only. Never in apps/web, never in logs, never in the repo.

What we claim, and what we don't

Claim: this exact evidence record existed in this exact form at this time, and you can check it yourself.

Do not claim: that the measurement is correct, the sensor calibrated, the field report honest, or the AI right.

09

Oracle plan and its fallback

Target: Autonomous Database + bundled APEX + ORDS, one schema shared by the API and APEX. That shared schema is the Oracle proof — the stage moment is the enterprise console and the cinematic web app reading the same rows.

Dev from hour one: gvenzl/oracle-free (Oracle Database 23ai Free) in Docker Compose. Oracle-real SQL, zero provisioning wait.

Promotion: one connection string — oracledb thin mode plus a wallet for ADB. P3 verifies the swap before Gate 2, not on Day 2.

If ADB or APEX never lands

Demo on local Oracle 23ai Free, show the migrations and the APEX export, and say exactly that. A working local Oracle with honest framing beats a broken cloud claim — but we never describe local Oracle as "Autonomous Database".

GeoRaster: a 30-minute spike, a feasibility note, then stop. If it happens to work, one raster metadata query is a bonus beat at the very end. It is never a dependency.

OCI GenAI: needs trial credits in a supported region; Always-Free ADB alone does not include it. Hence the Gate 1 go/no-go.

10

UI quality — and the skills we use for it

It should look like something a climate fund would actually buy, not a hackathon dashboard. Three things get us there.

  1. Design system before pixels. FE-1 locks palette, type scale, spacing, motion durations and elevation, plus the provenance badge. shadcn/ui for primitives so nobody hand-rolls a dialog at midnight.
  2. Charts as evidence, not decoration. Uncertainty drawn as bands. Valid-pixel fraction encoded, not hidden. Honest axes — no truncated y-axis to dramatise the dip. One colour-blind-safe series palette across every beat.
  3. Motion that carries meaning. Transitions communicate time passing and spatial zoom. Everything else stays still, and prefers-reduced-motion is honoured.

11

Conventions and commands

  • TypeScript strict; Python type hints and Pydantic at every boundary.
  • Business logic out of React components and out of route handlers. Pure functions for NDVI, QA masking, canonicalization and alert rules — these are the testable core.
  • Repositories for all DB access. Bind variables only. No string-interpolated SQL, ever.
  • Migrations are versioned and forward-only. If it isn't in database/migrations, it doesn't exist.
  • Conventional commits prefixed with the task ID: feat(DA-9): divergence alert rule + tests.
  • Branch per task, PR into main. IN reviews everything; lanes cross-review each other's tests.
  • Structured logs with request IDs. Never log credentials, keys or document contents.

Tests that must exist by Gate 5

NDVI and QA masking · alert thresholds (fires / doesn't / suppressed) · canonical hash determinism · verification pass and fail · one API→Oracle integration test · one Playwright run of the nine beats.
